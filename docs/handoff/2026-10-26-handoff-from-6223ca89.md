## 2. 项目定位与硬约束

- **最终目标**（用户 10-24 提出）：把最初命令行 Agent 做成**桌面端应用**，界面参考 DeepSeek Harness。
- **模型策略**（用户明确纠正过一次，别搞反）：**API 模型是主力，本地 `qwen3.5:2b` 只是断网兜底**，不要拿"本地模型慢"当设计理由。
- **MCP / 联网能力必须是可选增强层**：断网、Server 崩溃、启动超时都不得影响文件、Office、会话、本地模型这些本地功能。
- 界面语言中文，风格延续现有深色三栏。

## 3. 架构

```text
React 界面（渲染进程，Vite + TS）
        │  HTTP + SSE
        ▼
FastAPI sidecar（Python，127.0.0.1 随机端口 + 随机 token）
        │
        ▼
graph_agent / 会话 / 子 Agent / 文件+Office 工具 / MCP 工具

Electron 主进程：启动 Python sidecar、开窗口、把 API 地址和 token 发给界面
```

## 附录：旧会话为什么废了

- 累积到 80 轮 / 2397 次工具调用 / 68 MB 日志；bili 估算单次请求 **110–200 万 tokens**，而 `deepseek-flash` 窗口 75–100 万。
- 代理的 preflight 自动折叠救不回来：摘要调用预算（32 次）耗尽，且组装出的摘要 8.9 万字符 > `maxSummaryLength` 2 万、又不比被折叠内容（7.3 万字符）更短，被判无效。
- 结果：`/compact`、重发「你好」全都发不出去，界面只剩「已停止」「已重试模型请求（1/5）」。
- 根因是**大返回直接进上下文**：subagent 的 `send_message`/`job_output`/大文件读取一次几十万字符，第 72 轮单轮就吃进 310 万字符。
- 教训：长会话里让子 agent 只回报结论、`job_output` 用摘要模式、大文件分页读，别把原始输出留在主上下文。
